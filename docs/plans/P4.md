## Tasks and acceptance tests

### P4.1 Movement (first; everything stands on it)

1. **Own fixed-step physics, not Arcade**, so `check-levels` runs the identical maths in Node. Pure `stepPlayer(state,
   input, config, dtMs)` at `stepHz`: gravity, walk, charge, launch, one-way platforms (land from above only).
2. **Charge (MOV-2):** a fresh `keys.jump` press while grounded charges; walking stops (assumption). Caps at
   `maxChargeMs`; release launches at `lerp(minSpeed, maxSpeed, charge01)`, `angleDeg` toward the held side, else up.
3. **Jump latch:** charging needs a press after a release. Every teleport (save load, ember return) sets the latch.
4. **Air steering (MOV-3):** held direction moves horizontal speed at most `airSteer01 × walkSpeed` away from the
   launch value, so a launch can never be reversed.
5. Scene: keys by `KeyboardEvent.code` from settings → input → step → draw. Camera uses `startFollow` and
   `setBounds` (both in `phaser.d.ts`), never the signal. Emit `jump`; `precision_window` true while charging (P7.3).

| Acceptance test | How |
|---|---|
| Deterministic arc | Unit: one input sequence run twice gives identical positions at every step. |
| Charge caps | Unit: holding 2 × `maxChargeMs` launches at exactly `maxSpeed`. |
| Steering cannot reverse | Unit: full launch right, hold left throughout: lands right of takeoff, within the cap. |
| Held key never relaunches | Unit: jump held through a teleport: no launch until release and a new press. |
| EEG cannot reach movement | `npm run check` passes the lane test; `rg -n composure src/game/player` prints nothing. |

### P4.2 Sections and stationary platforms (PLT-1, PLT-2)

1. `section-loader.ts` validates sections (unique ids, known `type`, zones inside the world, a full-width floor as
   section 1's lowest platform), naming the bad id.
   Registry: `'static'` → `{ stationary: true, anchorSafe: true }` (P6 anchors read this flag).
2. `check-levels.ts`: breadth-first search from the spawn platform. From three x positions on each platform, try
   three directions × 12 charge levels with `stepPlayer` (no steering, so conservative). Every platform, refuge and
   finish must be reached. Prints one line per section; exits 1 listing unreachable ids.

| Acceptance test | How |
|---|---|
| Levels pass | `npm run check:levels` prints `p0-low: all reachable`, `p0-high: all reachable`, exits 0. |
| Unreachable is caught | Unit: fixture with a platform 2000 px up → that id is reported. |
| Bad data is readable | Unit: unknown platform type, or no full-width floor → error names the id. |

### P4.3 Falling with no death (FAL-1)

1. A fall keeps going until you land on a platform or the floor: no teleport, no checkpoint return, no health,
   lives or death screen. The recovery ember (P6) is the only way back up. P4 never emits `section_reset`.
2. Every landing emits `land`; one at least `minFallPxToOffer` below the takeoff ledge also emits
   `fall { heightPx, big }` with `big = heightPx ≥ bigFallPx`.
3. `sectionAt(y)`: section *i* runs from its lowest platform up to section *i+1*'s lowest platform (derived, no
   field). Only `GameSnapshot.sectionId` uses it (P8's per-section look, P7); refuges and finish use their areas.

| Acceptance test | How |
|---|---|
| A fall always lands | Unit: drop from section 2's top → lands on a platform or the floor; `sectionAt` reads 1. |
| No reset | Browser: drop off section 2 → you land lower, in section 1 if nothing catches you. |
| Events fire | Unit, fake bus: a long drop emits one `land` and one `fall` with `big: true`. |

### P4.4 Refuges, saving, persistence, first ember (CHK-1 to CHK-3, EMB-1)

1. Entering a refuge saves at once, no signal condition: `{ v: 1, refugeId, emberAvailable, visitedRefugeIds }`
   under `lighten.save.v1`. Emit `refuge_enter { firstVisit }`, then `checkpoint_saved`. The checkpoint is the
   refuge you last entered: where a reload resumes (CHK-1, CHK-3). It is never a fall destination.
2. Start with one ember. A first visit refills to one (emit `ember_gained` only if it was 0); revisits do not.
3. `inRefuge` is true while inside: audio quiets (P5.4), P5.2 lights the refuge fully.
4. Boot resumes at the saved refuge (its section's `spawn`) with the saved ember; corrupt or missing → fresh run.
   `storage` is optional in `GameDeps` (in-memory default), so this merges before the `main.ts` line lands.

| Acceptance test | How |
|---|---|
| Round trip | Unit: save, load with the same fake storage → same refuge, ember, visited list. |
| Corrupt save | Unit: `{oops` in storage → fresh run, no throw. |
| Revisit gives nothing | Unit: visit, spend ember, visit again → still none, `firstVisit: false`. |
| Reload resumes | Browser: reach the refuge, reload → start at the refuge with the same ember. |

### P4.5 Finish and phase handling (END-1)

1. Entering `finish` emits `finish`, sets `'finished'`, stops input, clears the save (next player starts fresh).
2. Consume `pause`, `resume` (P2.2 emits them): `'paused'` stops stepping; `resume` restores the earlier phase.
3. `snapshot-writer.ts` publishes `sectionId`, `inRefuge`, `altitude01` (section 1 spawn = 0, finish = 1).

| Acceptance test | How |
|---|---|
| Finish fires once | Unit: a state inside the finish emits one `finish`; phase is `'finished'`. |
| Pause freezes | Unit, fake bus: no movement after `pause`; after `resume` it moves and an `'ember'` phase returns. |
| Whole loop | Browser: climb to the top of the test climb; the console shows `finish`. |
