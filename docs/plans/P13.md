## Goal

In `npm run dev`, press a key to enter edit mode, drag a ledge, and see the climb update at once. Ledges up to
and including the one you moved are stored. Ledges above it keep coming from the generator, which carries on from
the moved ledge with the same random draws it would have used anyway. Nothing above is re-rolled.

## The idea in one picture

The generator does not produce positions. It produces **steps**: "the next ledge is this far right and this far up
from the previous one".

```
platform 0 (floor) --step 1--> platform 1 --step 2--> platform 2 --step 3--> platform 3 ...
```

- A step's random numbers come from `hash(seed, index)`, never from a shared stream and never from
  `Math.random`. So step 7 draws the same numbers whether or not step 3 was edited.
- An edit file stores a **pinned prefix**: the steps for ledges 1 to k, as relative offsets.
- Building the climb: for ledge i, use the pinned step if `i <= k`, otherwise ask the generator for step i,
  giving it the real previous ledge.

Moving ledge k therefore changes one stored step. Every ledge above k is generated from the new ledge k: same
draws, so the same shape, carried along with the ledge you moved. That is "the generator carries on with its
normal duties".

One honest limit: the generator keeps ledges inside the side walls. If you drag a ledge far sideways, a ledge
above may be nudged to stay in bounds, so it is "same draws", not always "identical shape".

## Contracts (new, small)

`src/shared/contracts/content.ts`:

```ts
/** One ledge described relative to the ledge before it (centre to centre, world pixels, y grows downward). */
export interface LevelStep { dx: number; dy: number; width: number; height: number; type: string }

/** Saved editor output. pinned[i] is the step that places ledge i + 1; ledge 0 is the floor. */
export interface LevelEdits { version: 1; seed: number; pinned: LevelStep[] }
```

`src/shared/contracts/config.ts`: `GameConfig.generator` (seed, ledge count, ledges per section, step ranges in
pixels, ledge width range, `applyEditsInBuild: boolean`). Values live in `src/config/game.config.ts`.

No change to `PlatformData`, `SectionData`, the events or the stores. The generator's output is ordinary
`SectionData[]`, so the scene, the save, the ember, the level checker and protected visibility need no changes.

## Sub-phases (each is one claimable task)

### P13.1 Step generator (about 1.5 hours)

- `src/game/world/generator/step-generator.ts`: `generateStep(seed, index, previous, config): LevelStep`. Pure.
  Alternates sides, picks a rise and a width inside the configured ranges, keeps the ledge inside the walls, and
  stays inside the jump the player can make (ranges are tuned against `GAME_CONFIG.jump`, then proven by test).
- `src/game/world/generator/hash.ts`: a small integer hash to a number in 0..1, written in the file. No dependency.
- Acceptance: the same `(seed, index, previous)` always gives the same step; 50 seeds all pass
  `checkReachability` from `tools/levels/reach.ts`.

### P13.2 Layout resolver and the edit file (about 1 hour)

- `src/game/world/generator/resolve-layout.ts`: `resolveLayout(config, edits): SectionData[]`. Builds the floor,
  walks the steps (pinned, then generated), splits ledges into sections, places a refuge on the first ledge of each
  later section and the finish above the last ledge. Zones are stored as offsets from their ledge, so they move
  with it.
- `src/content/level-edits.json`: starts as `{ "version": 1, "seed": <n>, "pinned": [] }`.
- `src/main.ts` (shared file, one small commit): `?level=generated` uses `resolveLayout`; otherwise `SECTIONS`,
  unchanged. Edits are applied when `import.meta.env.DEV` is true or `applyEditsInBuild` is true.
- `tools/levels/check-levels.ts` also checks the resolved generated climb.
- Acceptance tests:
  1. Empty `pinned` gives exactly the pure generated climb.
  2. Pin ledges 1..k unchanged: the climb is identical (pinning alone moves nothing).
  3. Move ledge k by (dx, dy), away from the walls: ledges below k are unchanged, and every ledge above k is
     shifted by exactly (dx, dy). This is the "not regenerated" test.
  4. Changing a generator range in config does not move any pinned ledge.

### P13.3 Edit mode (about 2 hours)

- `src/game/editor/` (new folder): `edit-mode.ts` (toggle, pause physics, free camera), `drag-ledges.ts` (pointer
  drag with a grid snap), `apply-edit.ts` (pure: current layout + moved ledge to a new `LevelEdits`).
- Loaded only in dev: `if (import.meta.env.DEV) { const editor = await import('./editor/edit-mode'); ... }`.
- On drop: build new edits, call `resolveLayout`, rebuild the ledges in the scene, keep the player where they are.
  `drawWorld` must return what it drew so it can be redrawn (small change to `src/game/world/world-view.ts`).
- Rule when moving a ledge that already has pinned ledges above it: only that ledge moves (the next stored step is
  adjusted to compensate). Generated ledges always follow.
- A ledge that the reach check says cannot be reached is tinted red. This uses `reachable-ledges.ts` from PR 51
  once it is merged; until then run `npm run check:levels`.
- Entering edit mode clears the saved game, because a moved refuge would make a stale save point.
- Acceptance: `apply-edit.ts` has unit tests; a `run/dev-level-editor.mjs` run file lists the hands-on steps.

### P13.4 Saving, and proof the build is clean (about 1 hour)

- While editing, the layout is kept in `localStorage`, so a reload does not lose work.
- "Save to repo": a dev-only Vite plugin (`apply: 'serve'`, `configureServer`) in `vite.config.ts` accepts one
  local POST and writes `src/content/level-edits.json`. It exists only while `npm run dev` runs, so the rule
  "nothing on the demo path uses the network" holds. Fallback if this is not wanted: a "copy JSON" key.
- `tools/pipeline/build.mjs`: a new `editor` audit step that fails the build if any file in `dist/` contains the
  editor module's marker string.
- Acceptance: `node run.mjs build` passes and the new step reports "editor not in build"; the built game ignores
  the edit key.

## Deviation from the architecture rules, stated

The editor draws its own handles and a line of help text on the canvas instead of going through `src/ui/`. Reason:
it is a dev tool with no player-facing strings, and keeping it in one folder means deleting `src/game/editor/`
removes it completely.

## Risks

| Risk | What we do |
|---|---|
| The generator makes an unfair or impossible jump | Ranges proven by `checkReachability` over 50 seeds; red tint in the editor. |
| An edit breaks the climb above it | Generated ledges are built from the moved ledge, so the next jump is always inside the ranges. |
| Editor code leaks into the demo build | Dev-only dynamic import plus the build audit step. |
| Someone changes the hash or the order of draws | Every unpinned ledge moves. A snapshot test of one seed's layout guards it. |
| A generated climb replaces Neil's sections by accident | Authored stays the default; generated needs `?level=generated`. |
| It eats the last hours before freeze | See "Read this first", item 2. Cut order: P13.4, P13.3, P13.2, P13.1. |
